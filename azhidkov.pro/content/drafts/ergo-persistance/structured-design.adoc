== Введение

== Экспресс-курс Структурного дизайна

Структурный дизайн - это методология разработки ПО, созданная Ларри Константином и (#todo: #) в 60-ых годах прошлого века.

Самым известным наследием структурного дизайна стали понятия cohesion и coupling, которые до сих пор активно используются в нашей индустрии.

Но на мой взгляд, незаслуженно была забыта другая идея из структурного дизайна - в оригинале - это transform-centered morphology, но я буду называть это сбалансированной формой системы.

Идея предельно проста: при разработке код надо разделять на четыре типа - управляющий, код чтения данных, трансформацию и код записи данных.

И если систему, разработанную с разделением кода на эти типы, представить в виде структурной схемы, то получится примерно такая картинка:

image::2024-09-18-10-19-50.png[]

В книге Константин пишет, что соответствие системы этой форме напрямую коррелирует со стоимостью разработки и поддержки системы.
Системы, которые соответствуют этой форме, являются более дешёвыми в разработке и поддержке.

Давайте посмотрим, что будет если применить принципы структурного дизайна в современной разработке и приводить форму систем к сбалансированной.

== Кейс №1: Project Barcoder

И начнём мы с кусочка кода из Project Barcoder - внутренней системы предприятия для автоматизации бизнес-процесса архивации отчётных документов.

[NOTE]
====
Обобщённо процесс следующий:

. Филиалы предприятия собирают отчётность за один или более периодов в подручную тару (коробки, в коде - Box);
. Экспедиторы доставляют коробки в пункты сбора;
. Специалисты ПС переупаковывают документы из коробок в стандартизированные коробы (в коде - OsgBox);
. Специалисты ПС передают коробы в специализированную организацию для долговременного хранения;

Требования:

. В одной коробке могут содержаться документы за несколько отчётных периодов;
. В одном коробе могут содержаться документы за несколько отчётных периодов;
. Необходимо сохранять привязку из какой коробки в какие коробы попали документы за определённый отчётный период;

.. При переупаковке допустимы только два варианта:
... Переупаковка из одной коробки в несколько коробов;
... Переупаковка нескольких коробок в один короб
====

=== До применения принципов структурного дизайна

В этой системе, среди прочего есть примерно вот такой код:

[source,kotlin]
----
@Transactional
open fun repackage(boxIds: List<Long>, osgBoxes: List<OsgBoxDto>) {
    val osgIds = osgBoxes.map { it.osgBoxId }
    if (osgService.hasAnyLinks(boxIds, osgIds)) {
        throw OsgRepackageBoxAlreadyLinkedException("Some of the boxes and osg are already linked")
    }
    if (boxIds.size == 1) {
        repackageSingleBox(boxIds.single(), osgBoxes)
    } else {
        repackageMultipleBoxes(boxIds, osgBoxes.single())
    }
}

private fun repackageSingleBox(
    boxId: Long,
    osgBoxes: List<OsgBoxDto>,
) {
    val box = boxRepo.findByIdOrNull(boxId) ?: throw BoxNotFoundException("Короб не найден")
    box.reportingIntervals = toReportingIntervals(osgBoxes)
    boxRepo.save(box) // В проекте используется Spring Data JDBC, поэтому вызов save обязателен
    osgService.insertBoxesToOsgLinks(osgBoxes.map { it.osgBoxId }, listOf(boxId))
}

private fun repackageMultipleBoxes(
    boxIds: List<Long>,
    osgBox: OsgBoxDto,
) {
    boxIds.forEach { boxId ->
        repackageBoxToOsgBox(boxId, osgBox)
    }
    osgService.insertBoxesToOsgLinks(listOf(osgBox.osgBoxId), boxIds)
}

private fun repackageBoxToOsgBox(boxId: Long, osgPeriod: OsgBoxDto) {
    val box = boxRepo.findByIdOrNull(boxId) ?: throw BoxNotFoundException("Короб не найден")
    box.reportingIntervals.forEach {
        it.osgBoxId = osgPeriod.osgBoxId
    }
    boxRepo.save(box)
}
----

Этот код переупаковывает некие коробки (Box) в некие коробы (OsgBox).

Сначала он проверяет, что между запрошенными коробками и коробами нет существующих связей.

Затем в зависимости от параметров выполняет перепаковку либо одной коробки в несколько коробов, либо наоборот, несколько коробок в один короб.

И на первый взгляд с этим кодом вроде бы всё хорошо - он состоит из небольших аккуратных функций с одним уровнем абстракции и хорошими показателями coupling и cohesion.

Но внимательный читатель может разглядеть в нём проблему - метод `repackageBoxToOsgBox`, вызываемый в цикле в методе `repackageMultipleBoxes` содержит два обращения к БД - `findByIdOrNull` и `save`.
Что ведёт к тому, что мы тянем из БД, а потом сохраняем строчки по одной.

А как известно, пакетная работа с БД, когда строчки загружаются или сохраняются пакетом в одном запросе, намного более эффективна.

[NOTE]
====
Здесь код упрощён и причёсан во имя упрощения восприятия материала, соответственно в реальном коде обнаружить эту проблему было ещё сложнее.
====

Моя практика показывает, что "методом пристального вглядывания" далеко не все такие проблемы можно своевременно найти.

Давайте посмотрим, сможет ли нам помочь с этим структурный дизайн.

=== Приведение кода к сбалансированной форме

Я строю структурные схемы кода примерно раз в год.
Но для наглядности, давайте построим структурную схему текущей версии кода переупаковки:

image::images/../2024-09-18-09-41-11.png[]

Очевидно, форма этого кода имеет перекос в сторону вывода (афферентной ветки).

Давайте отрефакторим его к сбалансированной форме.

Первым делом надо заинлайнить весь код с io в корневой метод:

[source,kotlin]
----
open fun repackage(boxIds: List<Long>, osgBoxes: List<OsgBoxDto>) {
    val osgIds = osgBoxes.map { it.osgBoxId }
    if (osgService.hasAnyLinks(boxIds, osgIds)) {
        throw OsgRepackageBoxAlreadyLinkedException("Some of the boxes and osg are already linked")
    }
    if (boxIds.size == 1) {
        val boxId = boxIds.single()
        val box = boxRepo.findByIdOrNull(boxId) ?: throw BoxNotFoundException("Короб не найден")
        box.reportingIntervals = toReportingIntervals(osgBoxes)
        boxRepo.save(box)
        osgService.insertBoxesToOsgLinks(osgBoxes.map { it.osgBoxId }, listOf(boxId))
    } else {
        val osgBox = osgBoxes.single()
        boxIds.forEach { boxId ->
            val box = boxRepo.findByIdOrNull(boxId) ?: throw BoxNotFoundException("Короб не найден")
            box.reportingIntervals.forEach {
                it.osgBoxId = osgBox.osgBoxId
            }
            boxRepo.save(box)
        }
        osgService.insertBoxesToOsgLinks(listOf(osgBox.osgBoxId), boxIds)
    }
}
----

Теперь нам надо из самого большого if-а в конце метода вытащить чтение и запись данных.

С чтением всё просто - нам в обоих ветках надо превратить id-ы коробок в соответствующие объекты.
Это делается лёгким движением руки, путём замены `findById` на `findByIdIn`:

[source,kotlin]
----
@Transactional
open fun repackage(boxIds: List<Long>, osgBoxes: List<OsgBoxDto>) {
    val osgIds = osgBoxes.map { it.osgBoxId }
    if (osgService.hasAnyLinks(boxIds, osgIds)) {
        throw OsgRepackageBoxAlreadyLinkedException("Some of the boxes and osg are already linked")
    }
    val boxes = boxRepo.findByIdIn(boxIds)
    if (boxes.size == 1) {
        val box = boxes.single()
        box.reportingIntervals = toReportingIntervals(osgBoxes)
        boxRepo.save(box)
        osgService.insertBoxesToOsgLinks(osgBoxes.map { it.osgBoxId }, listOf(box.id!!))
    } else {
        val osgBox = osgBoxes.single()
        boxes.forEach { box ->
            box.reportingIntervals.forEach {
                it.osgBoxId = osgBox.osgBoxId
            }
            boxRepo.save(box)
        }
        osgService.insertBoxesToOsgLinks(listOf(osgBox.osgBoxId), boxes.map { it.id!! })
    }
}
----

И обратите внимание, что этим же движением руки, мы заодно перевели и чтение на пакетный (то есть более эффективный) режим работы.
Сама структура сбалансированной системы, в которой бизнес-логика может работать только с тем, что уже было загружено ранее, вынуждает разработчика делать io пакетно.

Теперь давайте перейдём к вытаскиванию вывода из бизнес-логики.
С непривычки это может показаться сложной задачей.

Однако разделение ввода-вывода и бизнес-логики характерно ещё и для функционального программирования (в плане баланса формы системы - правопреемника структурного дизайна) и у ФП для этой задачи есть стандартное решение - замена вызова метода с io на возврат параметров этого вызова.

Для того чтобы провернуть этот трюк давайте выделим if в отдельный метод:

[source,kotlin]
----
open fun repackage(boxIds: List<Long>, osgBoxes: List<OsgBoxDto>) {
    val osgIds = osgBoxes.map { it.osgBoxId }
    if (osgService.hasAnyLinks(boxIds, osgIds)) {
        throw OsgRepackageBoxAlreadyLinkedException("Some of the boxes and osg are already linked")
    }
    val boxes = boxRepo.findByIdIn(boxIds)
    repackBoxes(boxes, osgBoxes)
}

private fun repackBoxes(
    boxes: List<Box>,
    osgBoxes: List<OsgBoxDto>
) {
    if (boxes.size == 1) {
        val box = boxes.single()
        box.reportingIntervals = toReportingIntervals(osgBoxes)
        boxRepo.save(box)
        osgService.insertBoxesToOsgLinks(osgBoxes.map { it.osgBoxId }, listOf(box.id!!))
    } else {
        val osgBox = osgBoxes.single()
        boxes.forEach { box ->
            box.reportingIntervals.forEach {
                it.osgBoxId = osgBox.osgBoxId
            }
            boxRepo.save(box)
        }
        osgService.insertBoxesToOsgLinks(listOf(osgBox.osgBoxId), boxes.map { it.id!! })
    }
}
----

Теперь мы можем удалить из метода `repackBoxes` вызов `osgService.insertBoxesToOsgLinks`, добавить возврат двух списков, которые надо передать в этот вызов и перенести сам вызов в корневой `repackage`:

[source,kotlin]
----
fun repackage(boxIds: List<Long>, osgBoxes: List<OsgBoxDto>) {
    val osgIds = osgBoxes.map { it.osgBoxId }
    if (osgService.hasAnyLinks(boxIds, osgIds)) {
        throw OsgRepackageBoxAlreadyLinkedException("Some of the boxes and osg are already linked")
    }
    val boxes = boxRepo.findByIdIn(boxIds)

    val repackageResult = repackBoxes(boxes, osgBoxes)

    osgService.insertBoxesToOsgLinks(repackageResult.osgBoxIds, repackageResult.boxIds)
}

private fun repackBoxes(
    boxes: List<Box>,
    osgBoxes: List<OsgBoxDto>
): RepackageResult {
    if (boxes.size == 1) {
        val box = boxes.single()
        box.reportingIntervals = toReportingIntervals(osgBoxes)
        boxRepo.save(box)
        return RepackageResult(osgBoxes.map { it.osgBoxId }, listOf(box.id!!))
    } else {
        val osgBox = osgBoxes.single()
        boxes.forEach { box ->
            box.reportingIntervals.forEach {
                it.osgBoxId = osgBox.osgBoxId
            }
            boxRepo.save(box)
        }
        return RepackageResult(listOf(osgBox.osgBoxId), boxes.map { it.id!! })
    }
}

private data class RepackageResult(
    val boxIds: List<Long>,
    val osgBoxIds: List<Long>
)
----

Как видите, никакого рокет сайнса.
Единственно, что может показаться непривычным - для того, чтобы вернуть два объекта из `repackBoxes`, нам пришолсь завести "локальный" класс RepackageResult.

Теперь нам остался последний шаг - вытащить вызов `boxRepo.save` из метода трансформации `repackBoxes`.
Вообще я сторонник неизменяемой модели данных и по хорошему на мой взгляд, с коробками надо проделать тот же трюк, что и со связями - в `repackBoxes` создать новые экземпляры и вернуть их в RepackageResult.

Но мне кажется неизменяемые объекты ещё не стали мейнстримом и для того, чтобы оставить пример близким более широкой аудитории, оставим `Box` изменяемым.

И в этом случае мы можем использовать boxes как in-out параметр и просто заменить `boxRepo.save` в `repackBoxes` на `boxRepo.saveAll` в repackage:

[source,kotlin]
----
fun repackage(boxIds: List<Long>, osgBoxes: List<OsgBoxDto>) {
    val osgIds = osgBoxes.map { it.osgBoxId }
    if (osgService.hasAnyLinks(boxIds, osgIds)) {
        throw OsgRepackageBoxAlreadyLinkedException("Some of the boxes and osg are already linked")
    }
    val boxes = boxRepo.findByIdIn(boxIds)

    val repackageResult = repackBoxes(boxes, osgBoxes)

    boxRepo.saveAll(boxes)
    osgService.insertBoxesToOsgLinks(repackageResult.osgBoxIds, repackageResult.boxIds)
}

private fun repackBoxes(
    boxes: List<Box>,
    osgBoxes: List<OsgBoxDto>
): RepackageResult {
    if (boxes.size == 1) {
        val box = boxes.single()
        box.reportingIntervals = toReportingIntervals(osgBoxes)
        return RepackageResult(osgBoxes.map { it.osgBoxId }, listOf(box.id!!))
    } else {
        val osgBox = osgBoxes.single()
        boxes.forEach { box ->
            box.reportingIntervals.forEach {
                it.osgBoxId = osgBox.osgBoxId
            }
        }
        return RepackageResult(listOf(osgBox.osgBoxId), boxes.map { it.id!! })
    }
}
----

Этим мы заменили множество UPDATE-запросов на один пакетный запрос.

== Кейс №2: Project Daniel

Напрямую описать предметную область Project Daniel я не могу из-за соображений NDA, поэтому возьму схожий по сути, но вымышленный пример.

Project Daniel - это коробочное решение для служб VIP-такси.
Клиенты оставляют заказы на поездку, система по сложному алгоритму подбирает для него водителя и назначает на заказ.
Далее водитель везёт клиента.

Очевидно, ключевой функцией системы является функция назначения водителя на заказ.
И так как у нас VIP-такси, для принятия решения она использует множество различных данных и правил - время ожидания клиента, время простоя водителя, статус клиента, навыки водителя, историю взаимодействия конкретной пары клиента и водителя и т.д.
Так же VIP-персоны не привыкли долго ждать, поэтому ожидают, что машины им будут назначать за пару секунд и если это не так - уходят к конкурентам.

=== До применения принципов структурного дизайна

При разработке Project Daniel, команда руководствовалась общепринятыми принципами дизайна - преимущественно идеями Роберта Мартина в виде Чистого кода и принципов SOLID.

И команда действительно изо всех сил старалась сделать код максимально чистым - буквально на каждом втором ревью разворачивались многодневные баталии о том, насколько тот или иной код чист и сколько ответственностей у того или иного класса и метода.

И тем не менее, спустя пять лет разработки качество реализации функции назначения водителей на заказ.

Всего в реализации этой функции несколько тысяч строк кода и даже без учёта НДА, было бы бессмысленно иллюстрировать этот кейс кодом, поэтому сразу приведу оригинальную структурную схему:

image::2024-09-18-12-26-17.png[]

Не знаю как у вас, а у меня один вид этого графа вызывает ужас.
Он настолько большой и запутанный, что мне не удалось хотя бы примерно раскрасить его в соответствии с типами кода сбалансированных систем.

Я могу сказать, что читать и поддерживать этот код было очень сложно, но это будут голословные и субъективные утверждения.

Зато у меня есть медицинский факт об этом графе - он до жути медленный.

Функция назначения водителя работала как фоновая задача - она запускалась раз в секунду, просматривала очередь заказов и выполняла назначения.
И за одну секунду она успевала просмотреть только очередь из пяти заказов.

Долгое время это всех устраивало.
Однако на опытной эксплуатации у нового стратегического покупателя Project Daniel очередь заказов дорастала до нескольких тысяч заказов.

И время ожидания назначения машины выросло до нескольких минут.
И это ставило под угрозу покупку продукта новым клиентом.

Поэтому продакт поставил команде задачу ускорить работу этой функции.

При ближайшем рассмотрении "внезапно" оказалось, что всё тормозит на работе с БД - все данные тянулись поштучно и для обработки очереди из тысячи заказов эта функция делала тысячи запросов в БД.

Поэтому решили навести порядок в коде с помощью приведения формы этой функции к сбалансированной.
Если точнее - с помощью экстренного переписывания этой функции с нуля.

И мы справились.
Через две недели после старта работ, мы выкатили в опытную эксплуатацию новую версию, которая за секунду уже могла обработать очередь из 1500 заказов.

== Кейс №3: Project E

Кейсы Project Barcoder и Project Daniel были хороши тем, что в них менялась только одна переменная - форма системы.
Соответственно можно с высокой долей уверенности говорить о том, что позитивные изменения в структуре кода и его производительности вызваны изменением формы системы.

Аналогичного кейса ещё большего масштаба, где я бы взял целое приложение и поменял бы в нём только форму системы у меня нет.

Но есть кейс где я взял целое приложение на 150 HTTP-эндпоинтов и 40К строк Kotlin кода и переписал его с нуля, в процессе чего среди прочего следил за сбалансированностью формы системы.

Сам проект, причины и ход его реинжиниринга и методика получения цифр для оценки результатов приведены у меня в двух отдельных постах.
Но не буду отправлять вас читать их целиком и дам прямо здесь краткий пересказ.

Project E - это медицинский дневник, разработанный по заказу производителя мед. оборудования.

Изначально проект разрабатывала одна команда на C# и микросервисной и вертикальной архитектуре силами одного мидла.
Но по определённым причинам, заказчик заморозил разработку примерно на 90% готовности первой версии.
А когда решил возобновить разработку, изначальная команда отказалась продолжать работы и проект достался мне.

По началу я примерно три-четыре месяца пытался развивать оригинальный проект, но по ряду причин (описаны тут) у меня это получалось плохо.
Поэтому я решил переписать проект на Kotlin и монолитной и функциональной архитектуре (пересекающейся со структурным дизайном в плане сбалансированной формы) силами трёх юниоров.

А после того как мы это проделал благополучно проделали и три месяца поработали над развитием новой версии, я покопался в JIRA и выяснил, что средние трудозатраты и количество ошибок на задачу сократилось в три раза.

В этом случае значение формы системы уже не очевидно, но моё субъективное мнение: оно есть.
И чем дольше система растёт и развивается, тем больше оно будет возрастать.

== Как научиться делать сбалансированные системы

Надеюсь, мне удалось хотя бы кого-то убедить в том, что форма системы имеет существенное значение на стоимость её поддержки.
Стоимость как в нервных клетках разработчика, так и рублях бизнеса.

И в этом случае может возникнуть вопрос - "А как *мне* научиться разрабатывать сбалансированные системы?".

К сожалению, "Структурный дизайн" не будет ответом - объективно эта методология умерла.
По ней невозможно найти современной информации, а оригинальные источники показывают свой 60-летний возраст.

Однако разделение ввода-вывода и бизнес-логики является краеугольным камнем ещё и функционального программирования - которое сейчас цветёт и пахнет и о котором сейчас публикуется множество книг.

Функциональное программирование бывает разное.
Бывает как на Haskell - с монадами, аппликативами, сигнатурами вида `findUser(): Future<Try<Option<User>>` и хвостовой рекурсией вместо циклов.

А бывает такое, как в https://github.com/ergonomic-code/Project-Mariotte/blob/master/src/main/kotlin/mariotte/apps/guest/reservations/ReserveRoomOperation.kt#L90[Project Mariotte] - которое практически не отличишь от "обычного" программирования.

Поэтому тем, кому ближе прагматичный подход к разработке, для обучения разработке сбалансированных систем я могу порекомендовать следующий ридлист:

. https://t.ly/YNCr0[Grokking Simplicity]
. https://t.ly/B_flt[Принципы юнит-тестирования]
. https://t.ly/RhCaG[Java to Kotlin: A Refactoring Guidebook]
. https://t.ly/uwFIt[Domain Modeling Made Functional]
. https://t.ly/7_Njg[Data-Oriented Programming]
. https://t.ly/QaMDu[Структура и интерпретация компьютерных программ]
. https://t.ly/foQRZ[Functional Design: Principles, Patterns, and Practices]
. https://t.ly/BHhpa[Structured Design]
