== Аннотация

Идёт 24-ый год: анкл Боб написал https://www.amazon.com/Functional-Design-Principles-Patterns-Practices/dp/0138176396["Functional Design: Principles, Patterns, and Practices"], в Java планомерно завозят фичи из ФП языков - лямбды, рекорды, паттерн матчинг, закрытые иерархии -, функцоинальный стиль можно теперь встретить не только в хипстерском стартапе, но и https://www.youtube.com/watch?v=YBsihlkI1E8&list=PLVe-2wcL84b88Ec7BFQZ5aEcu_h6U9isn&index=4[крупном банке].

Уже можно констатировать, что хайп ФП прошёл, а ФП осталось.

Однако в разработке бакендов в ФП стиле, есть слон, который лёгким движением хобота может разнести всю лавку к чертям - JPA.

В этом докладе я расскажу, что вас ждёт, если вы решите быть в тренде и, потренировавшись писать неизменямые списки и функции с хвостовой рекурсией, пойдёте писать в ФП-стиле свою обычную молотилку данных, лежащих в РСУБД.

И как жить, если у вас отобрали контекст транзакции, ленивую загрузку и даже оператор "=", а вы не знаете что такое "моноид в категории эндофункторов" и знать не хотите.

== Почему ФП

Объяснить чем ФП хорошо - ещё сложнее, чем объяснить что такое "моноид в категории эндофункторов".

Постов и докладов на эту тему миллион, среди которых есть и https://azhidkov.pro/posts/23/10/why-fp/[мой].

В своём я апеллирую к исследованиями 60-ых годов, которые показали сильную корреляцию структуры программ, похожей на функциональную и низкой стоимостью их разработки:

[quote, Larry Constantine, "Structured Design, p. 144"]
____
It [transform-centered model] was derived empirically from a careful review of the morphology of systems, comparing systems that *had proven* to be *cheap to implement, to maintain, and to modify* with ones that had been expensive.

 [...]

The umpteenth round in this game produced what came to be called the transform-centered model.
*Most of the cheap systems had it* - none of the costly systems did!

---

Она [модель, ориентированная на трансформацию] была получена эмпирически на основе тщательного анализа морфологии систем со сравнением систем, которые *были доказано дёшевы в разработки, обслуживании и модификации*, с системами, которые были дорогостоящими.

 [...]

Энный раунд этой игры породил то, что стало называться моделью, ориентированной на трансформации.
*Она присутствовала в большинстве дешёвых систем* - ни одна из дорогостоящих систем не имела её!
____

То есть ФП экономит ваши нервы и деньги бизнеса.

override operator fun invoke(roomReservationRequest: RoomReservationRequest): ReservationSuccess {
    log.info("Processing room reservation request: {}", roomReservationRequest)

    val reservation = reservationFromRequest(roomReservationRequest) 

    // Ввод
    val reservationRequestDate = LocalDate.now() 

    if (!ReservationRules.canAcceptAt(reservation, reservationRequestDate)) { 
        throw ReservationDatesInPastException(reservation.from)
    }

    val hotel = hotelsService.findById(roomReservationRequest.hotelId) 
    log.info("Hotel: {}", hotel)
    if (hotel == null) {
        throw EntityNotFoundException(Hotel::class, roomReservationRequest.hotelId)
    }

    val capacity = hotelsService.getCapacityForUpdate(hotel.ref(), reservation.roomType) 
    log.info("Capacity: {}", capacity)
    if (capacity == null) {
        throw EntityNotFoundException(RoomType::class, hotel to reservation.roomType)
    }

    val reservationsByDate =
        reservationsRepo.getReservationsAmountPerDate(
            hotel.ref(),
            reservation.roomType,
            reservation.from,
            reservation.to
        )
    log.info("Reservations by date: {}", reservationsByDate)

    // Трансформация/чистая функция/бизнес-логика
    if (!ReservationRules.hasRequiredFreeRooms(capacity, reservationsByDate)) { 
        throw NoAvailableRoomsException(hotel.ref(), reservation.roomType, reservation.from, reservation.to)
    }

    // Вывод
    val persistedOrder = reservationsRepo.save(reservation) 

    return ReservationSuccess(persistedOrder.id) 
}

private fun repackageBoxes(
   boxes: List<Box>,
   osgPeriods: List<OsgPeriodDto>
): Pair<List<Box>, BoxOsgBoxLinks> = when {
   boxes.size == 1 && osgPeriods.all { it.periods.isEmpty() } -> {
       val box = boxes[0]
       listOf(box.unlinkReportingIntervalsFromOsg()) to NoLinks
   }
   boxes.size == 1 && osgPeriods.all { it.periods.isNotEmpty() } -> {
       val box = boxes[0]

В общем давайте представим, что я убедил вас попробовать ФП стиль.

В этом случае, первое с чем вы столкнётесь, решив написать свой бэк в ФП стиле: JPA с ним категорически не совместима.

== Почему JPA никогда не подружится с ФП

По спецификации.

В спеке зашито изменение через мутацию полей:

    An update to the state of an entity includes both the assignment of a new value to a persistent property or field of the entity as well as the modification of a mutable value of a persistent property or field
    — JSR 338: JavaTM Persistence API; Version 2.2; "3.2.4 Synchronization to the Database"

== Если не JPA, то что?

В мире Java (+Kotlin) есть несколько достойных на мой взглдя доверия фреймворков/библиотек работы с БД, поддерживающие работу с неизменямой моделью данных: jooq, MyBatis, Exposed (Kotlin) и Spring Data JDBC.

Среди них Spring Data JDBC обладает DevX, наиболее близким к Spring Data JPA, плюс последние 4 года свои проекты я делаю на нём, поэтому в докладе иллюстрации я тоже буду делать на нём.

Однако большая часть информации, техник и проблем будет актуальной для любого фреймворка с поддержкой неизменяемой модели.

== Пример

В качестве примера, давайте возьмём небольшой проект информационной системы фитнес-зала, написанный в стандартном стиле на базе JPA и постепенно переведём его на неизменяемую модель, хранимую с помощью Spring Data Jdbc.

==== Связи *-to-Many

Так как у нас больше нет конструктора по умолчанию и сеттеров, мы потеряли ленивую загрузку.
И получили проблему: здесь для того чтобы поменять имя тренера, мы загрузим ещё и сотни его программ, с сотнями упражнений, с тысячами шагов, с тысячами картинок:

image::images/../2024-06-21-11-46-43.png[]

И чтобы попилить модель на небольшие агрегаты я предлагаю использовать такой алгоритм:

. Завести явные сущности для связей Many-To-Many
. Разделить (в голове/на бумажке) связи *-to-Many и *-to-Few
. Связи *-to-Many поменять на Many-To-One (обратить); связи *-to-Few можно оставить как есть.

=== Вводим границы агрегатов для Spring Data Jdbc

Проблема: при обновлении агрегата Spring Data JDBC бай дезигн удаляет все не корневые сущности и вставляет их заново.

Решение удивительное и неоднозначное, однако за 4 года мне ни разу не пришлось заняться его оптимизацией и концептуально его вполне можно обосновать - представьте, что постгрес - это мапа record-ов, и вам по сети прилетело новое дерево рекордов, вы его положили в мапу, а старарое дерево собрал GC.

Тем не менее, когда мы попытаемся вставить упражнение - что-то взорвётся.
(#todo: щяс уже наверняка не помню, то ли вообще ещё на страте при построении мета модели, то ли при попытке сохранения агрегата из-за попытки удаления строки, на которую есть ссылки.#).
